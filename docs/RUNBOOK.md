# Runbook: rebuild, collectors, release, recovery

Read /etc/motd and the host rules first (shared login node: heavy work goes to Slurm, `mltheory`, `--exclude=node302`, explicit
`--mem`, `--time`, `--cpus-per-task`; `sbatch --test-only` before submitting; do not poll the controller: chain jobs with `--dependency=afterok:` and read their output files, or use `atlas pipeline ... --wait` / `atlas release --wait`, which make one `sacct` call per 120 s or more; a manual `squeue`/`sacct` check is never more often than every 120 s).
Set up a shell: `. /n/fs/resemble/homogenizing-science/code/paths.sh` (gives `$CS_ATLAS_PY` and every path).

## Rebuild

1. Everything committed on `main` (a release refuses uncommitted tracked build files). Land branches first
   (`tools/agent_worktree.sh land <name>`; docs/CONTRIBUTING.md).
2. Is a trial worth it? Trial builds never write live data: `PI_HIERARCHY_OUT=<scratch>` (`tools/scratch.py path <name>`).
   Old-vs-new on the same inputs: `OLD=<commit> REPORT=<dir> [SCHOOLS="..."] [VALIDATE=1] sbatch hierarchy/build-equivalence.slurm`
   from the new checkout; the report lists every changed field and the accepted lab-page papers wired or set aside.
3. Full rebuild on Slurm from the code root: `atlas submit --test-only hierarchy/rebuild-all.slurm`, then `atlas submit hierarchy/rebuild-all.slurm`
   (it pins main's HEAD as the job's code, so a landing during the run cannot change it: docs/CONTRIBUTING.md; about 1-2 h; log `hierarchy/logs/rebuild-all-<jobid>.out`). Subset: `STAGES="build audits" SCHOOLS=mit bin/atlas rebuild`.
4. Exit 0 all good; 1 a stage failed (read the log from the first `FAILED`); 2 regression swings blocked the release.
   `hierarchy/BUILD-REGRESSION.md` says which counts moved. If the swing is intended (a rule change, accepted additions), re-run
   the release with `ALLOW_SWINGS=1`; the release records that. If not, find the cause before anything else.
5. `atlas validate` (also a stage): a violation holds the release. Fix the writer, not the schema, unless the schema is wrong
   (`schemas/`, docs/DATA-DICTIONARY.md is generated from them).
   Tell a stale file from a writer bug before fixing anything: `ls -l --time-style=long-iso` the violating file against `git log -1 --format=%ci -- tools/pihier/` and the builder commit
   that fixed that kind of finding. A file written before the fix (2026-11-02: string and 2099 years, `asof` as `2026012820`, a 2015 year, all fixed in the builder on 2026-10-31) is
   regenerated by the next rebuild, never hand-edited; one written after it, or a file no builder writes (the lab-page additions come from `tools/labpage_audit.py`), points at the writer.

## Collectors

- Seven loops, one per school with a store, as one Slurm array (task 0-6, Michigan is 6): `atlas submit fulltext-push/downloads.slurm`
  (from the code root; `--array=N` for one school; pins main's HEAD). `hierarchy/COLLECTORS-STATUS.md` (regenerated after every round) shows each loop's job, phase, last round,
  attempts and downloads in 24 h. Check it before touching anything.
- Stop a loop: `scancel <jobid>` (SIGTERM; the running pass stops cleanly and loses nothing, tried URLs are recorded).
  A loop that idles backs off from 10 minutes to 4 hours by itself.
- **Loops restart themselves** (ROADMAP #18, `fulltext-push/loop_job.sh`): Slurm sends USR1 to the batch script 900 s before the
  3-day limit (`--signal=B:USR1@900`); the script stops the loop with TERM (lock released, pass stopped cleanly), then runs
  `atlas submit --test-only` and, unless it prints `Preempts:`, `atlas submit fulltext-push/downloads.slurm --array=<n>`, which
  pins main's HEAD at that moment. The line `{"loop_job": ...}` in `<store>/loop.log`/`lab_first_loop-<school>.out` says what
  happened; a refused or failed resubmit leaves the loop down (the status page alarm). `scancel` (TERM) stops for good: no resubmit.
  Michigan's collector job restarts as `downloads.slurm --array=6`, the loop alone. Proof: `tests/test_loop_job.py`.
- **Download yield (2026-11-03).** A loop only asks the collector for candidates its catalog holds, once each. Three things keep
  open copies out of reach and are handled in code: (1) `downloads.slurm` runs the channels `ledger_found` and `reader_link` before the
  loop, so the release's new open copies and the reader's confirmed links become candidates; (2) a timeout / 500 is asked again for the
  priority papers (`priority_retry.py`, at most twice per URL, 6 h apart); (3) an HTTP 429 is a timed cooldown shared by all loops
  (`host_throttle.py`, raw/host-throttle.json: 5 min, doubling per 429 within 2 h, cap 1 h; up to 15 min is waited out, longer pauses the
  host for the pass) instead of a pause for the rest of the pass, and dspace.mit.edu / infoscience / bioRxiv / medRxiv / Wayback keep one
  request clock across loops. MIT's DSpace file store (`cf003.cdn.4science.cloud`, path-limited) is an approved delivery host.
  A change in `collector_wrapper.py` or `lab_first_loop.py` reaches a loop only when it restarts.
- A second loop for the same store exits at once (`<store>/.loop.lock`); `flock -n <store>/.loop.lock true` tells whether it is free.
- Never run a writer that does not take the catalog lock (Princeton importer, vendored Infoscience/DSpace resolvers) while that
  store's loop runs (docs/STORES.md). Do not `du` or walk `stores/`; use `df`.
- Failed attempts: diagnose from the catalog's attempts table and `loop.log`; `fulltext-push/requeue_causes.py` requeues by cause
  and logs every row it deletes under `staged/`.

## Pipelines (the mechanical chains)

`atlas pipeline --list` shows them. `atlas pipeline copies` runs lab_paper_copies per school (a Slurm array), then the unavailability ledger, the coverage recount and
the collectors status page; `atlas pipeline labpage` runs the lab-page audit per school, restamps the acceptance files and writes the summary; `atlas pipeline reader`
the reader export. Each stage is submitted `afterok` the one before, from a code snapshot of main's HEAD, so nothing is polled and nothing is typed between stages;
`--test-only` checks the first stage, `--wait` blocks until the chain ends with one `sacct` call per 120 s or more (tools/slurm_wait.py; it stops at the first failed job) and prints the states, `atlas pipeline status` shows a run. A new chain is a new entry
in `PIPELINES` in tools/atlas_pipeline.py. The hand checks, the design and the diagnosis of a failed stage stay with the agent.

## Release

`atlas release` runs the whole chain and stops at the first failure: **preflight**, rebuild, **regression, then validate** (validate reads the file the regression
writes), reader export, release (with the generated CHANGES.md), notes check, organized tree, GitHub export (written and committed locally), then the two steps
that publish outside this host, `export-push` (tag `release-<id>` and push) and `hf-upload`, and last the Codex handoff note (SITE-HANDOFF.md, added to the
release). The two external steps need `--yes-push` / `--yes-hf` (or a "y" at the terminal); without them the run stops with exit status 3 and `--resume`
continues after you confirm. `atlas release --dry-run` prints the steps.

**It runs on Slurm by default** (ROADMAP #37 v2, 2026-11-03): `atlas release [options]` submits `hierarchy/release.slurm` from main's HEAD (`sbatch --test-only`
first, refused on `Preempts:`) and blocks on it with one `sacct` call per 120 s or more (`--wait` is accepted and means the same; `atlas submit
hierarchy/release.slurm` with `RELEASE_ARGS` in the environment is the same job). `--local` runs it in your own process on the login host: opt-in only, because the
login host's memory budget is shared (the job asks 4 CPUs, 32 GB). Run dir and state: `<scratch>/release-<jobid>/run.json`.

**Before any build, the fast preflight** (about as long as the test suite: measured below) fails everything that used to fail after a 35-60 minute rebuild,
all at once, in parallel: main clean; the full test suite inside a `git archive` snapshot with the release's own environment (`STAGES`, `TAG`, `RELEASE_ARGS`,
`CS_ATLAS_SNAPSHOT_COMMIT` exported, the same `rebuild.sh STAGES=tests` the rebuild runs); `validate` and the evidence check on the current files (outputs
`preflight-*` in the run dir, the live files untouched); the regression check of the current files against the last release; and an `sbatch --test-only` of the
build array. **Swings are signed off up front**: the preflight prints every regression swing with its id (`kind|school|pi-or-count`) and fails on any that is
not approved. Approve with `--allow-swings` (all), or `--swings-file FILE`, a JSON file `{"signed_by": "...", "signed_at": "YYYY-MM-DD", "swings": ["<id>", ...]}`
listing the ids you read (an unsigned file approves nothing). The regression step after the build accepts the same approval, so a swing never first fails at
minute 70. `atlas release --preflight-only` runs just this (nothing is built or frozen).

**The rebuild is recorded stage by stage** (snapshot, build, zero_paper, ids, copies, ledger, audits, evidence, tests): each is written to `rebuild_stages` in
run.json when it ends, and `--resume --tag <tag>` starts at the failed stage, not at the top. A commit that changed since the failed run may resume only when it
touched nothing outside `tests/` and `docs/`: the run prints and records a `NOTE: resuming across commits ...` (a changed `tests/` also re-runs the tests stage and
the preflight); any other change is refused, start a new tag. **The build stage is the per-school Slurm array** (`hierarchy/build-school.slurm`, newest school
first, `sbatch --test-only` first; `--array-throttle N` limits tasks at once, ~15 min instead of ~35); `--serial-build` builds the schools one after another in the
release job. `zero_paper` (tools/zero_paper_ledger.py) is a rebuild stage right after the build: the site's build needs a ledger row per hidden lab.

**One release at a time**: the run takes the lease `atlas-release` (`atlas lease status atlas-release` shows holder, host, job; a heartbeat renews it, it is released
on exit and on `scancel`). A second release, from any host, is refused with the holder's name; if the holder is certainly gone, `atlas lease release atlas-release --force`.

`hierarchy/rebuild.sh` takes `STAGES=... SCHOOLS=... TAG=... BEFORE=... ALLOW_SWINGS=...` as arguments as well as environment variables, `--list` prints the resolved
stages and schools, and any other argument or unknown stage name is refused (exit 2); it never silently runs a full rebuild.
A release is `releases/<date>[.N]/`, read-only, with `MANIFEST.json` (hashes, code commit, rules, counts, regression, ledger, ids, reader) and `CHANGES.md`;
`releases/latest` points at the newest. Releases are never overwritten or edited; notes are added only with `make_release.py add-note` (`atlas make-release`
cuts just the release). Agents do not push; the coordinator confirms the external steps.

## Refresh the recent OpenAlex works (ROADMAP #24; before each release)

The sweeps (`hierarchy/<school>/raw/openalex-sweep.sqlite`) and `pi-works.sqlite` are API snapshots of the day they were pulled; OpenAlex then creates, changes and
merges records (2026-11-04: Princeton's API held 7,804 works of 2026, the sweep 7,506). Refresh the current year (and last year) before a release. This key has no
`from_updated_date` / `from_created_date` filter and no updated/created sort (HTTP 429 "Plan upgrade required"), so a refresh re-pulls the years under the sweep's own filter.
1. Budget: the shared key is 10,000 credits a day (`fulltext-push/raw/openalex_budget.jsonl` is the ledger; one list request = 1 credit, 200 works). One year of all
   schools is about 900 credits papers-only; datasets (20-75% of a school's 2026 records, not papers) are skipped with `type:!dataset`, their stored rows stay. Plan at most 2 UTC days.
   `tools/oa_api.py` is the only client: it masks the key in every message and traceback, appends the ledger line, stops at the run's `--cap` or the shared `--floor`.
2. Fetch (Slurm, one stream, ~1.2 s a request, resumable): `sbatch --export=ALL,SNAPSHOT_REPO=<worktree>,CS_ATLAS_SNAPSHOT_COMMIT=<sha>,OA_ARGS="fetch <schools> --years 2026 --cap N" tools/oa_refresh_works.slurm`
   (or `atlas submit` from main once landed). Output: `<SCRATCH>/oa-refresh-<tag>/<school>.sqlite`. `--years 2025,2026` adds last year; PI author ids come from `pis.json`.
3. Scratch rebuild BEFORE: `tools/oa_refresh_build.slurm` (array over the schools, `OUT=<scratch>/build-before`): the builder on the unchanged stores.
4. Merge, dry run then `--apply` (local, a few minutes; backups of every replaced row go to `<stage>/backup-<school>.sqlite`):
   `$CS_ATLAS_PY tools/oa_refresh_works.py merge <schools> --years 2026 [--apply]`. The report per school: API count (all types, papers) vs ours before/after,
   new, changed, dropped (merged ids: the same DOI under a fresh id, else `--lookups N` singleton lookups follow the redirect), new PI-credited works, pi-works rows.
5. Scratch rebuild AFTER (`OUT=<scratch>/build-after`), then count `lab_papers.jsonl.gz` per school and read ten new lab papers (right PI, school, appointment).
6. Copies: `add_works.py <school>` for each school, then Princeton's package through `vendor/princeton_tools/import_all_when_free.py`, then the channel run
   (`fulltext-push/addworks-<date>.slurm`; CORE API use is enabled for every school under the 2026-11-15 owner decision). The next release rebuilds from the refreshed stores.
First run 2026-11-05: 1,445 credits (2026 papers 809 incl. PI works, 2025 papers 570, counts and probes the rest), one UTC day; singleton lookups (merged-id redirects) cost 0 credits and run
per school in parallel (`--years 2025+2026`: sbatch --export splits on commas). Ids the API no longer returns: DOI match or redirect = merged (dropped), 404 dropped, still alive but not credited = kept ("alive", 1-5% of a year).
Slurm needs `SNAPSHOT_REPO=<worktree>,CS_ATLAS_SNAPSHOT_COMMIT=<sha>` in --export until the branch is landed. add_works reads live `lab_papers.jsonl.gz`, so before a release rebuild it runs on a scratch hierarchy root of symlinks
(`fulltext-push/addworks-1105.slurm`, `AFTER=<scratch>/build-after`), queued after the running addworks job.
Snapshot-swept schools (uchicago, gatech: their sweep meta says `snapshot:<date>`) get the snapshot's own keep rule applied to the API records (per-affiliation exclusion, related-id gate).

## Recovery

| what went wrong | what to do |
|---|---|
| A rebuild wrote bad packages | the previous packages are in the last release (`releases/<id>/hierarchy/<school>/`, read-only) and in the rebuild's snapshot `scratch/pkg-before-<tag>/` (kept for the newest two rebuilds). Copy back the five package files, never into a release. Then find why: `hierarchy/BUILD-REGRESSION.md` |
| A reviewed input was changed badly | it is in git: `git log -p -- hierarchy/<school>/<file>`; revert on a branch and land it |
| A bulk change to a store catalog | `stores/<school>/backups/catalog.<reason>-<date>.sqlite` (latest two kept) and the append-only logs under `staged/` (requeued, reverted, restored rows); quarantined files are renamed, never deleted (`quarantine/*/manifest.jsonl`) |
| A branch landed something wrong on `main` | `git revert` it on a branch and land the revert; `main` only moves by fast-forward, no force |
| A loop died or the host rebooted | `squeue -u $USER`; resubmit only the missing array task(s) of `downloads.slurm` (`--array=<n>`) after checking `COLLECTORS-STATUS.md` and the lock |
| The build is not deterministic between two runs | the builder's output depends on str hash order in places; compare with the same `PYTHONHASHSEED` (the equivalence job fixes it to 0) |
| Ids changed | they must not: `hierarchy/ids/registry.sqlite` travels with every release; restore it from the last release (docs/IDS.md) |
| Moved files, old paths | `archive/migrations/*.jsonl` records every move of the project relocation; `tools/relocate_project.py` and `tools/relocate_data.py` are dry runs by default |

## Starting or restarting an agent (leases and the restart checklist; ROADMAP #17, #40)

Every agent holds one lease while it works (`atlas lease`, tools/agent_lease.py; files in `<root>/leases/`). A second copy of the same agent refuses to start
while the lease is live, so a restarted session cannot run beside a forgotten one. In this order:
1. `atlas lease status`: is the agent's lease live? A live lease of another session means that session is still working: stop and ask the coordinator.
   An expired lease (renewed more than 30 min ago) is free.
2. `atlas lease acquire <name> --note "<what I am doing>"` (exit 3 = refused). Renew on every report: `atlas lease renew <name> --note "<step>"`.
3. Read the hand-off: `docs/ROADMAP.md` for your rows, the memory index, and the last report.
4. Find your own state, not someone else's: `tools/agent_worktree.sh ls` (your worktree and branch, with uncommitted changes), `git -C <worktree> status`, `squeue -u $USER`
   (your jobs and the download loops; never cancel what is not yours) and `hierarchy/COLLECTORS-STATUS.md`.
5. Work in your worktree, land with `tools/agent_worktree.sh land <name>`; submit jobs with `atlas submit` / `atlas pipeline`; never commit on main (enforce is on).
6. At a clean stop, hand the work over (a note, branch names, job ids) and `atlas lease release <name>`. A crashed agent needs nothing: its lease expires.

## Restart checklist (ROADMAP #40)

Run it at every restart of a session or agent (usage limit, crash, host reconnect, handover), in this order, before touching anything. Each line says
what to look at and what not to do.

1. **Other sessions.** The host runs several sessions and agents at once, in separate worktrees, all against one data tree.
   - `atlas lease status` (live = another session is working: stop and ask the coordinator), `tools/agent_worktree.sh ls` and `git worktree list` (whose branch
     is whose, which have uncommitted changes), `squeue -u $USER` and `pgrep -u $USER -af 'python|atlas|rebuild'` on this host (what is running; an agent's loop or
     job may belong to a session that is gone or to one that is still alive).
   - Never cancel, kill or "clean up" what you did not start; never `git stash`, commit or reset in another agent's worktree or in the main checkout. Local processes
     die with their host: on a different login node the list above is not the whole picture (`hostname`; the collectors run on Slurm, not on a login node).
2. **Agent handover.** Read the previous agent's note first: `docs/ROADMAP.md` rows, the coordinator's last message, and the branch it names. A good note has the branch and worktree,
   uncommitted files (or a `WIP:` commit, docs/CONTRIBUTING.md "Handing off uncommitted work"), job ids, locks held, and what must not be touched until a job ends.
   If a note is missing, reconstruct from `git log <branch>`, the job logs and `hierarchy/COLLECTORS-STATUS.md`; do not re-run a step whose output exists.
   Take a lease (`atlas lease acquire <name> --note ...`) only after step 1 shows nobody holds it. At a clean stop write the handover and `atlas lease release <name>`.
3. **Re-create the auto-resume check.** It is session-only: the recurring check that wakes an agent after a usage limit (every 30 minutes, DECISIONS 2026-11-01) lives
   in the session that made it, and a new session, a reconnect or a host restart starts without it. So: look at what the session already has scheduled (do not add a second one),
   and if there is none, create it again with `/loop 30m <prompt>`. The prompt does one cheap thing: `atlas lease renew <name>`, ONE `squeue -u $USER` (or `sacct -j <ids>`), read the
   output files of the jobs it waits for, and continue the next item of the handover note; it never submits, cancels or restarts anything by itself, and it stops itself when the work
   is done. Cancel it at a clean stop. Never let two checks run for one agent.
4. **Never run a job on live code.** A landing rewrites many files in the main checkout in one go; a process that imports from it can see half a commit
   (2026-10-31, docs/CONTRIBUTING.md). Slurm jobs run from a snapshot of one commit: submit with `atlas submit`, `atlas pipeline` or `atlas release --wait`, never bare `sbatch` on a
   script that does not source `tools/job_code_snapshot.sh` (`tests/test_slurm_snapshot.py`). Local runs: from your own worktree (`bin/atlas ...`, `$CS_ATLAS_PY tools/x.py`), never from the main checkout while
   a landing may happen, and nothing long (a build, a collector) on a login node. The job log's first lines name the commit (`code snapshot: commit ...`).
5. **Loops stopped or restarted on the current commit.** A download loop keeps the code it loaded until it restarts. After a restart:
   - `git -C <code root> rev-parse --short HEAD` against each loop's log line `code snapshot: commit <sha>` (`hierarchy/COLLECTORS-STATUS.md`, `<store>/loop.log`). A loop on an older commit that the landing did not touch
     can stay; one whose commit lacks a fix you rely on is restarted: `scancel <jobid>` (TERM, no resubmit), wait for the lock to free (`flock -n <store>/.loop.lock true`), then
     `atlas submit --test-only fulltext-push/downloads.slurm --array=<n>`, and `atlas submit` it unless it prints `Preempts:`. A loop that restarts itself (USR1 at 900 s before its limit) already pins the then-current HEAD.
   - A loop that is down and was not stopped on purpose is resubmitted the same way, one array task at a time, after the lock and the status page say it is down. Never start a second loop for a store.
6. **Locks and journals.** Locks are `flock`s: they free themselves when the process dies, so a lock file that exists proves nothing; test it (`flock -n <file> true`) and never delete one.
   The ones to know: `<store>/.loop.lock` (one loop per store), `<store>/.catalog-write.lock` (a writer waits up to 30 minutes), the node-local `$CS_ATLAS_LOCKS` (gone with a reboot), the lease lock, per-channel locks in `FT_LOGS`.
   Journals: a SQLite `-journal`/`-wal` next to a catalog means a writer died mid-transaction; do not remove it and do not copy the database without it: open the file once for writing so SQLite rolls it back
   (`tools/relocate_data.py --settle-journals` does this for the project's files), then check `PRAGMA integrity_check` on a copy for anything large. Progress journals are kept: a release's
   `<scratch>/release-<tag>/run.json` (resume with `atlas release --resume --tag ...`, same options), a pipeline's `jobs.json` (`atlas pipeline status`), the requeue and revert logs under `staged/`. Read them before redoing a step.
7. **Tools on the PATH.** A restarted shell has nothing on its PATH: `. paths.sh` first (`$CS_ATLAS_PY`), and for the site `PATH=$CS_ATLAS_NODE/bin:$PATH` before `npm` (Node 22 in `env/site-node`, docs/ENVIRONMENT.md); never `conda install` anything.
8. Only then pick up the work, in your own worktree, and report.

## Reuse source research and batch school repairs

Use the same `CS_ATLAS_*` data overlay as the candidate build. After the baseline
PI build, create a finite research board in a private scratch directory:

```sh
bin/atlas closeout research sjtu --out /absolute/scratch/research-v1.json
```

The planner reads existing PI/student data, reviewed student evidence and declared
lab-page leads. It inspects the recall capture store read-only and reuses exact,
hash-matched `source_capture`/saved-file pointers. It does not search directories,
fetch sources, submit jobs or change scientific inputs. Missing originals remain
recovery work. A saved file never becomes a fresh HTTP response.

Work through whole current and dated-alumni sections, starting with sparse PIs.
Use `shared_sources` to read a common URL once, then judge its individual PI
contexts separately. New member observations stay proposals until normal source
review approves their School, role, date and identity scope. One quoted name does
not establish that an entire roster has been checked.

Generate a bounded batch from the current inventory instead of hand-selecting
or refetching pages. This refreshes and validates prior receipts first:

```sh
bin/atlas closeout research-batch sjtu --previous /absolute/scratch/research-v1.json --batch-size 20 --out /absolute/scratch/source-batch.json
```

The batch groups exact URL/source versions and carries each PI's complete case
and binding separately. Saved sources for sparse labs come first. Missing leads
remain individual tasks; a recorded refusal is never a request to retry that host.
`capture_stores` names the existing registered stores; source bytes remain there.
Successful saved responses precede saved redirect/error/challenge bodies, which
remain visible as `readable_saved_source: false`; a cached response body alone
does not establish readable roster evidence.

For each completed case, retain its `id` and `binding` and explicitly fill:

```json
{
  "status": "resolved",
  "coverage": "whole_source",
  "outcome": "reviewed",
  "reviewer": "independent-source-reviewer",
  "date": "2026-11-16",
  "why": "Complete current and dated-alumni sections checked; scope holds recorded in receipt.",
  "receipt": {"path": "/absolute/scratch/source-review.json", "sha256": "<actual report SHA-256>"}
}
```

Put those completed cases in a separate `{"school": "sjtu", "cases": [...]}`
review file, including each case's unchanged `id` and complete `binding`. Register
them through the command below; this checks all cases and receipt hashes before
writing, preserves existing decisions, and recomputes totals. Do not manually
edit a board's case status or summary.

```sh
bin/atlas closeout research sjtu --previous /absolute/scratch/research-v1.json --reviews /absolute/scratch/source-reviews.json --out /absolute/scratch/research-v2.json
```

A changed source, policy, PI context, missing receipt or repeated case stops the
whole registration. Neither sharing a source nor sharing a report approves a
second PI automatically. Existing output files are never overwritten.

`outcome` can also be `no_roster` or `unavailable`, with the actual search/access
limit described in `why` and the receipt. A positive review needs preserved source
bytes. Several explicitly reviewed cases can cite one report; its hash is read
once per validation pass. These are research-work receipts, never membership
approval, an automatic lab-page hand round, a student-match verdict or a signoff.
An initial pending case means no qualifying checkpoint has been registered on
this board. Existing complete source reviews can supply the receipt after their
source and PI/context bindings are checked; creating a board does not require
repeating that research or invalidate an existing gate.

Refresh the board after finishing a source batch or receiving new leads:

```sh
bin/atlas closeout research sjtu --previous /absolute/scratch/research-v1.json --out /absolute/scratch/research-v2.json
```

Unchanged source/PI/policy bindings retain their explicit review receipts. Changed
source bytes, capture years, appointments or identity context reopen work; a new
native student count alone does not. Existing output files are never overwritten.
The inventory covers known sources, not an exhaustive search of the web.

Consolidate genuine source corrections and holds before a full build. The closed
board can be passed to `atlas closeout seal sjtu --run-dir <new-run> --repairs
<board>`; sealing recomputes its inventory and checks all receipt hashes. New or
unfinished source work stops the seal. Complete ordinary input review and commit
requirements as well. If reviewed inputs are unchanged, check `atlas stale sjtu`
and the existing candidate before submitting another expensive chain: code and
raw stores may have changed separately. After the final build, keep the existing
fresh sample, independent review and accuracy requirements.

`atlas closeout plan <school>` includes the current source preflight. Stages 0
(charter, access and snapshot) and 1 (historical faculty sources) must pass, or
carry an existing owner-authorized gate exception, before sealing or running the
native chain. A worker that fails this preflight records `preflight_failed` and
runs no native phases. The derived `hosts.json` inventory is sealed along with
source inputs; changing it also invalidates execution and certification.
Inspect `closeout stages`, finish the source repair batch,
then seal a new run. Diagnostic research builds can still use the ordinary build
tools; they do not become a certified closeout. Stage advancement preserves each
gate's measured result but marks downstream stages as waiting until all their
prerequisites are complete, including transitive dependencies.
Stage 9 requires complete SHA-256 bindings for all five files used by the accuracy
drawer, in both `files` and `files_now`, and compares them with the live package.
Missing/partial bindings, non-finite probabilities and changed bytes fail the gate;
the existing precision and coverage thresholds remain unchanged.

If only an audit implementation needs correction after all native phases finish,
use `bin/atlas closeout fork-audits sjtu --from-run <finished-run> --run-dir <new-run>`.
This refuses changed/unsealed inputs, changed outputs or charters, dirty code,
an existing review draw, a live producer, or code changes outside a small audit
allowlist. It also compares the original closeout producer controls. The new seal
retains the native producer's actual code pin and records the new audit pin;
the original run stays intact. Submit the new run normally: diagnosis, student
audit and all prerequisite gates run again, while build/copies/ledger are reused.
Certify the exact successful job before the ordinary fixed independent sample.
Builder or evidence changes still require a new native build.

An exact, still-bound paper uncertainty hold explains why its candidate cannot
provide a student-paper link. Link diagnosis records the hold decision IDs only
when every otherwise unexplained candidate PI work is held. An unheld candidate
or missing link to an admitted lab paper stays open. Holds never admit a paper,
create a link, prove a student's publication identity, or carry a recall verdict.
